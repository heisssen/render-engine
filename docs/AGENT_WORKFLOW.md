# Агенти Claude Code для монтажу

Інструкції проєкту — у `CLAUDE.md`, спеціалізації — у `.claude/agents/`.
Це маршрут виконання завдань, а не фоновий сервіс: файли агентів самі нічого не запускають.
Після додавання файлів перезапустіть Claude Code у цьому проєкті.
Викликайте `/montage <завдання>` або потрібного агента за ім'ям у запиті.
Команда описана в `.claude/commands/montage.md`; координатор збирає результат і перевіряє залежності.
Економія контексту залежить від завдання: запуск усіх агентів для дрібної правки може збільшити витрати.
Модель основної сесії — Sonnet (`.claude/settings.json`); моделі спеціалістів задані явно у frontmatter.
Haiku збирає прості факти, Sonnet виконує роботу, Opus залучається лише для складного рішення.
Аліаси вибирають моделі, доступні поточному акаунту; це не фіксація конкретного покоління чи ціни.
Явний `--model`, локальні/керовані налаштування або змінні середовища можуть перевизначити модель.
Якщо роутинг відрізняється, перевірте `/model` і конфігурацію, не запускайте роботу повторно навмання.
Формат звірено з [агентами Claude Code](https://code.claude.com/docs/en/sub-agents)
та [налаштуванням моделей](https://code.claude.com/docs/en/model-config).

## Як ставити завдання

Приклади запитів:

> Через edit-planner перевір монтаж бітів 12–18: темп, вставки й цитовані сторінки.
> Виправ конфігурацію та перевір її. Озвучення й рендер зараз не потрібні.

> Запусти монтаж на наявних матеріалах до короткого прев'ю бітів 12–18.
> Використай edit-planner, asset-provenance і render-qa; незалежні перевірки можна виконати паралельно.
> Нові платні озвучення не генеруй.

> /montage Виправ темп бітів 12–18 та зроби коротке прев'ю на наявних матеріалах.

> Підготуй фінальний фільм із наявної озвучки: перевір монтаж, мікс і джерела,
> зроби прев'ю змінених сцен, а потім повний рендер із provenance gate.

Запит визначає межі робіт. Аналіз репозиторію не означає замовлення платної озвучки чи повного рендера.
Якщо ці дії вже входять у завдання, окреме повторне підтвердження не потрібне.
Коли бракує матеріалу, агент називає конкретний файл/біт і продовжує незалежні перевірки.

## Розподіл роботи

| Агент / модель | Читає за потреби | Зона відповідальності |
| --- | --- | --- |
| `project-scout` / Haiku | Preflight, вузькі фрагменти файлів | Лише читання: інвентаризація й конкретні факти |
| `edit-planner` / Sonnet | STORY, обрані біти JSON, монтажні правила | План кадрів, вставки, сторінки, переходи, темп, planner |
| `audio-pipeline` / Sonnet | Потрібні абзаци, manifest/placement, аудіоскрипти | Озвучка, вирівнювання, субтитри, мікс, дубляж |
| `asset-provenance` / Sonnet | Посилання на матеріали, sidecar/джерела | Наявність, атрибуція, ліцензії, ledger і gate |
| `render-qa` / Sonnet | Змінені компоненти, timings, скрипти рендера | Картинка, збірка, прев'ю, перевірка результату |
| `edit-director` / Opus | Короткий виклад складного питання й докази | Лише читання: рішення при неоднозначності, потім передача Sonnet |

Координатор призначає одного власника кожного файла/генерованого виходу перед делегуванням.
Наприклад, `edit-planner` володіє `timings.json` і `placement.json`, а `audio-pipeline` їх лише читає
після завершення planner. Не запускати одночасно команди, які перезаписують спільні результати.
У разі дозволеної паралельної роботи перевірка джерел і аналіз компонентів можуть бути незалежними.
Озвучка → alignment → остаточні timings → мікс/рендер залишаються залежними етапами.

Пакет завдання агенту має містити лише:

1. Потрібний результат і критерій готовності.
2. Релевантні файли, біти або діапазон кадрів.
3. Дозволені записи та власників спільних файлів.
4. Уже встановлені факти, перевірки й межі авторизації.
5. Формат відповіді: зміни, перевірки, блокери, наступна дія; до 12 пунктів.

Не пересилати всім агентам повний сценарій, усі біблії, JSON, геодані чи історію логів.
Починати з `rg`, витягувати потрібні ключі JSON, читати конкретні розділи правил.
Для невеликої правки достатньо одного агента. Повторно залучати того самого спеціаліста з коротким дельта-завданням.

## Порядок монтажного проходу

1. З'ясувати результат: аналіз, зміни конфігурації, прев'ю чи фінальний фільм.
   Перевірити `git status --short` і запустити `py -3.12 scripts/montage_preflight.py`.
   Це стислий JSON без запису файлів: структура, інструменти, залежності й наявність голосових takes.
   Звичайний режим блокує структурні помилки; `--require-ready` також блокує відсутні передумови.
   Preflight не замінює перевірку всіх медіа, ліцензій або відповідності кешованого рендера.
   Свіжий клон не містить відео, фото, сканів, музики й голосових take-файлів.
2. `edit-planner` перевіряє відповідність абзаців, manifest і STORY; знаходить конкретні проблемні біти.
   Правила читати з відповідних розділів `docs/bibles/`, не завантажувати всі документи наперед.
3. `asset-provenance` перевіряє використані джерела. Нові джерела мають отримати коректні записи й кредити.
4. Змінювати лише потрібні дані. Для змін озвучки виконати наведений нижче цикл.
   Для суто візуальних змін не повторювати TTS та alignment.
5. Після остаточних timings оновити залежні аудіо/субтитри, якщо змінилися їхні позиції.
   Виконати статичні перевірки та provenance gate.
6. `render-qa` збирає актуальний bundle і, коли це входить у завдання, рендерить короткий діапазон.
   Візуально перевіряє текст/кадрування/переходи; звук перевіряється окремо прослуховуванням.
7. Повний рендер виконати лише в межах замовленого результату.
   Звіт має називати готовий файл, виконані перевірки та невиконані перевірки з причиною.

## Команди й залежності

Команди запускати з кореня, послідовно перевіряючи успіх кожного етапу.
Для Python тут використано Windows launcher `py -3.12`; на інших платформах потрібен відповідний Python.

| Етап | Команда |
| --- | --- |
| Повторна озвучка біта, якщо замовлена | `py -3.12 en/voice.py --only 12` |
| Початкове розміщення голосу | `node en/timings.mjs` |
| Alignment і субтитри | `py -3.12 en/subs.py` |
| Початки речень | `py -3.12 en/sentences.py` |
| Остаточні cuts і placement | `node en/timings.mjs` |
| Числовий запис років у субтитрах | `py -3.12 en/subs_years.py` |
| Мікс | `py -3.12 en/mix.py` |
| Provenance gate | `py -3.12 tools/provenance.py --project . --lang en` |
| Збірка | `npm.cmd run bundle` |
| Прев'ю, приклад 10 секунд | `powershell -File scripts/preview_en.ps1 -Bundle out/bundle -From 0 -To 299` |
| Фінальний рендер | `powershell -File scripts/render_en.ps1 -Gate -Bundle out/bundle` |

`--only 12` — індекс із manifest, а не довільний номер абзацу в редакторі.
Цей прапорець примусово оновлює take 12, але скрипт також генерує всі інші відсутні takes
і прибирає застарілі MP3. Перед запуском перевірити індекс, повноту кешу та відповідність обсягу замовленню.
Не використовувати `subs.py --only` для фінального повного набору: цей режим перезаписує вихід вибраними бітами.
Перший запуск whisper може завантажувати модель. Відсутній кеш не означає миттєвий локальний крок.
Операції завантаження шрифтів/геоданих, terrain та перекладу запускати лише коли потрібні поточному завданню.

Після зміни коду/даних потрібен актуальний bundle. Для окремої версії:
`npx remotion bundle src/en/index.tsx --out-dir out/bundle-review`.
Передайте цей самий шлях через `-Bundle` у прев'ю/рендер.
Наявні `out/en/parts/partNN.mp4` пропускаються за фактом існування навіть з новим bundle.
Спершу визначити, чи це продовження тієї самої версії. Для іншої версії зберегти попередні результати
та відокремити старі parts перед рендером; не вважати зміну `-Bundle` очищенням кешу.
Supervisor і battery guard не запускати автоматично для прев'ю.

## Перевірки перед передачею

- Без npm-залежностей: `node scripts/check_imports.mjs`.
- Змінені Node-скрипти: `node --check en/timings.mjs` або шлях конкретного `.mjs`.
- Змінені Python-файли: `py -3.12 -m py_compile <file.py>` з явними шляхами.
- Тести Python: `py -3.12 -m unittest discover tests -v`.
- TypeScript та імпорти після встановлення залежностей: `npm.cmd run check`.
- Для медіарезультату: provenance gate, короткий render за потреби, перевірка наявності та тривалості виходу.

Поточний CI перевіряє Python, Node syntax/imports і секрети; TypeScript потрібно перевіряти окремо.
`--report-only` завжди повертає успіх і не замінює gate; `--no-hash` годиться для діагностики, не фінального ledger.
Статична перевірка не доводить, що фільм переглянуто чи звук прослухано.

Кеш перекладів тепер враховує модель, інструкції, текст і сусідні репліки. Старий кеш одного разу
не збігатиметься з новими ключами; наступний переклад може знову витратити токени.
Повторення ідентичного запиту використовує новий кеш; сама зміна таймкодів його не скидає.
